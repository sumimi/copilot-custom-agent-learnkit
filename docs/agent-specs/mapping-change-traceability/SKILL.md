# 変更トレーサビリティのマッピング

変更仕様の要求と、既存または変更予定の設計、ソースコード、ユニットテストとの対応関係を整理するときに、このスキルを使用してください。

## 目的

以下の関係を明示的に管理します。

`Requirement → Design → Source → Unit Test`

トレーサビリティによって、レビュー担当者が少なくとも次の問いに答えられる状態にしてください。

* この要求によって、どの設計が影響を受けるか
* この要求に関係するソースコードはどこか
* この要求を確認するユニットテストはどこか
* まだ特定できていない対応関係は何か

すべての項目を無理に埋めることではなく、変更要求と既存資産との関係、および不明点を明示することを重視してください。

## Requirement ID

独立して追跡する必要がある要求には、それぞれ Requirement ID を割り当てます。

変更仕様書に Requirement ID が定義されている場合は、その ID を使用してください。

変更仕様書に Requirement ID が存在しない場合は、分析用の ID として次の形式で連番を割り当ててください。

* `CR-001`
* `CR-002`
* `CR-003`

Requirement ID を追加するためだけに、変更仕様書そのものを書き換えてはいけません。

Requirement ID は、分析資料および `traceability.md` の中で管理してください。

## traceability.md の形式

`traceability.md` では、原則として次の形式を使用してください。

| Requirement | Requirement Summary | Design | Source | Unit Test | Status |
| ----------- | ------------------- | ------ | ------ | --------- | ------ |

各 Requirement について、1つ以上の対応関係を追跡できるようにしてください。

1つの Requirement が複数の設計、ソースコード、ユニットテストに関係する場合は、読み手が対応関係を判断できる形で記載してください。

## Requirement Summary

Requirement Summary には、変更仕様書の内容を簡潔に要約してください。

変更仕様書に存在しない要求を追加してはいけません。

要約と推測を混同しないでください。

要求自体に不明点がある場合は、Status や別途管理される Open Question で明示してください。

## Design の記録方法

Design には、Requirement と関係する設計ドキュメントを記録してください。

可能な限り、ファイルだけではなく関連する章・節まで特定してください。

推奨する記載例:

`docs/order-design.md - リトライ処理`

ファイルのみを記載するよりも、具体的な箇所を示すことを優先してください。

ただし、確認できていない章・節を推測して記載してはいけません。

要求と設計ドキュメントとの意味的な関係を確認してから対応付けてください。

ファイル名やキーワードが似ているという理由だけで、関係があると判断してはいけません。

## Source の記録方法

Source には、Requirement と関係する既存ソースコードを記録してください。

可能であれば、次の粒度まで特定してください。

* ファイル
* クラス
* 関数
* メソッド

推奨する記載例:

`src/order/OrderService.ts - retryOrder()`

ファイルのみを記載する場合:

`src/order/OrderService.ts`

ソースコードを対応付ける際は、そのコードが Requirement に関係する既存動作を実際に担当していることを確認してください。

ファイル名や識別子に同じ単語が含まれているという理由だけで対応付けてはいけません。

設計フェーズでは、変更予定のコードと既に変更済みのコードを混同しないでください。

## Unit Test の記録方法

Unit Test には、Requirement と関係する既存ユニットテストを記録してください。

可能であれば、次の粒度まで特定してください。

* テストファイル
* テストクラス
* テストケース

推奨する記載例:

`tests/order/OrderServiceTest.ts - retryOrder_whenTimeout`

既存テストが存在しない場合は、存在しないことを明示してください。

存在しないテストケースを、既存テストとして記載してはいけません。

今後追加する予定のテストは、既存テストとは区別して扱ってください。

例えば次のように記載できます。

`Planned: タイムアウト時に再試行されることを確認するテスト`

## 不明な対応関係

調査しても対応関係を特定できない場合は、推測で値を埋めてはいけません。

対応関係を特定できない場合は `TBD` を使用してください。

要求または設計上の判断が未解決であるため対応関係を決められない場合は、`Needs Clarification` を使用してください。

不正確な対応関係を書くよりも、不明であることを明示することを優先してください。

## Status

設計フェーズでは、原則として次の Status を使用してください。

* `Analyzed`
* `Design Updated`
* `Needs Clarification`
* `TBD`

### Analyzed

変更要求と既存資産との関係を調査済みであることを表します。

### Design Updated

Requirement に必要な設計変更が設計ドキュメントへ反映済みであることを表します。

### Needs Clarification

要求や設計判断について、人間による確認が必要であることを表します。

### TBD

調査を行ったものの、現時点では対応関係を特定できていないことを表します。

設計フェーズでは、実装完了を意味する Status を使用してはいけません。

## 既存情報と予定情報の区別

トレーサビリティでは、次の情報を混同しないようにしてください。

* 現在存在する設計
* 今回変更した設計
* 現在存在するソースコード
* 今後変更する予定のソースコード
* 現在存在するユニットテスト
* 今後追加・変更する予定のユニットテスト

特に、Implementation Plan に記載された予定を、既に実装済みであるかのように traceability.md に記録してはいけません。

## トレーサビリティの検証

トレーサビリティの作成または更新後は、次の項目を確認してください。

1. 変更仕様書から識別したすべての Requirement が traceability.md に存在する
2. 各 Requirement について既存設計との関係を調査している
3. 各 Requirement について既存ソースコードとの関係を調査している
4. 各 Requirement について既存ユニットテストとの関係を調査している
5. 特定できなかった対応関係が明示されている
6. traceability.md と現在の設計ドキュメントに矛盾がない
7. 変更予定のソースコードを変更済みとして扱っていない
8. 追加予定のテストを既存テストとして扱っていない
9. ファイル名やキーワードの一致だけを根拠として対応付けていない
10. 変更仕様書に存在しない Requirement を追加していない

## 完了の考え方

トレーサビリティは、すべてのセルに値が入ったときに完成するものではありません。

次の状態になっていることを重視してください。

* 確認できた対応関係が明示されている
* 確認できなかった対応関係が明示されている
* 変更要求から設計、ソースコード、ユニットテストを追跡できる
* 予定と現状が区別されている
* レビュー担当者が Requirement ごとの影響範囲を確認できる

不確実性を隠さず、レビュー可能な状態にすることが、このスキルの目的です。
